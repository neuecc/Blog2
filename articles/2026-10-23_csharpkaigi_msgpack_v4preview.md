## MessagePack for C# v4 preview.1

ここずっと延々と作っていたのですが、無事なんとかpreview.1のリリースにこぎつけました！

* [https://github.com/MessagePack-CSharp/MessagePack-CSharp/releases/tag/v4.0.0-preview.1](https://github.com/MessagePack-CSharp/MessagePack-CSharp/releases/tag/v4.0.0-preview.1)

previewの更に前の、最初のプロトタイプで大炎上が発生して苦しい出発だったのですが、なんとかやり切ることができました。普通だったら心が折れてると思うので、自分がどういうポジションから言ってるのかを認識して、きちんと他人にはリスペクト持って発言して欲しいところですね。

と、それはともかくとして、謳い文句は

* Performant by default
* Secure by default
* Schema-resilient by default

です。そう、セキュリティです。昨今のAIによる攻撃は死ぬほど激しくて、旧来の造りでの継ぎ接ぎパッチではやってられない状態になっています。これは今思ったことではなくて、5月頃にMythosをこっそり使わせてもらってレビューを入れたときに思ったことです。Mythosのレビュー内容が、というよりも、それに対してAI生成で雑パッチをが当たった時に、これを延々と繰り返すのは無理だな、と。そしてAIによる分析力を活かしたパフォーマンス向上が見込めそうだというのも合わせて、パフォーマンスとセキュリティを向上させることで、ある程度の破壊的変更が許される(許して欲しい！）v4が始動できそうだ、と。

で、パフォーマンスについて。性能はデータによって変わってくるところもあるのですが、大きめのPOCOのシリアライズで見てみるとこんな感じです。

![](/article_img/20261023_1.jpg)

文句なく速い、です！シリアライザってかなり縮めるの難しくて、ドングリの背比べみたいな性能バトルになりがちなのですが、圧倒的にちぎってます。話題になったCapcomのRE EngineのREDoxのシリアライザーと比べても全然高速です。

色々な秘訣があるのですが、一番代表的なところではシリアライザーのインターフェイスの変更（これが破壊的変更の最大の要因）があります。

```csharp
public interface IMessagePackFormatter<TWriteBuffer, TReadBuffer, T>
    where TWriteBuffer : struct, IWriteBuffer, allows ref struct
    where TReadBuffer : struct, IReadBuffer, allows ref struct
{
    void Initialize(MessagePackFormatterResolver resolver);

    void Serialize(ref TWriteBuffer buffer, ref SerializeState state, T value);

    void Deserialize(ref TReadBuffer buffer, ref DeserializeState state, ref T value);
}
```

v3 ではバッファの型は固定で、すべてのフォーマッターが`ref MessagePackWriter`と `ref MessagePackReader` を受け取っていました。しかしシリアライザーの入出力は多様です。`Span<byte>`、`IBufferWriter<byte>`、`ReadOnlySpan<byte>`、`ReadOnlySequence<byte>`、その他色々。教科書的なオブジェクト指向の答えは、それぞれを抽象化する `IWriter` / `IReader` インターフェイスを用意することです。しかしシリアライザーのバッファ操作ではそれは選択肢になりません。バイト単位の操作ごとに仮想呼び出しが入るコストは大きすぎます。

そこで v3 の `MessagePackWriter` と `MessagePackReader` は、PipeReader/PipeWriterを想定した `IBufferWriter<byte>` と `ReadOnlySequence<byte>` を第一級の表現として扱う struct でした。その結果、ひとつの struct があらゆる入出力の形を扱わなければならなくなりました。struct は肥大化し、ロジックは複雑になり、if 分岐だらけになりました。v4 ではバッファの型そのものをジェネリックパラメータとして渡すようになっています。入出力の型ごとに最短経路が用意され、すべての呼び出し箇所でバッファの型が具体的な struct になるので、devirtualization とインライン化が保証されます。シリアライザーはメッセージひとつにつきバッファ操作を何万回も呼ぶことがあるので、これはパフォーマンスに大きな影響があります。

さらに、個々のフォーマッターは Dynamic PGO の guarded devirtualization が確実に効くような形にしてあります。v4は、モダンなC#とモダンなランタイムが100%性能発揮するように調整しているというのが今までとの大きな違いです。.NETのバージョンアップによる最適化で偶然性能が良くなった！ではなくて、.NETのバージョンアップによる最適化が確実に効くように、調整しきっています。これをやりきれたのが、まさにAIの力で、何度も何度も出力されるasmを確認して、最適化が効く形に修正していったのです。

もう一つ、Deserialize(int)のベンチマーク結果を紹介します。プリミティブのシリアライズというのはそれなりにやる機会が多いのと、もう一つは対象が小さいことにより、シリアライザーのセットアップコストだけを純粋に計測できるというところが注目しているところです。

というわけで、圧倒的に速いんですが、それがちゃんと理由で見えるんですよね、命令数が少ないから速いという、当たり前のことです。機能を保ちながら命令数を削る、それが最適化です。

ところであともう一点、「lastEntry キャッシュ」について。これって何かというと、最後に使ったコンバーター(`Converter<T>`)を一つだけキャッシュしています。
これやるとベンチマークには効きます、単一の`T`で`Serialize<T>`とか`Deserialize<T>`を回すから、ルックアップコストが丸ごと省けます。でも、実際のアプリケーションでシリアライザーに渡ってくる`T` ってバラバラに決まってるんですよね。だから、こういうのはベンチマークハックであり、やるべきでないことだと思っています。しかも別にタダじゃないですしね、毎回分岐予測を招くので通常のケースでは性能低下するだけ、という。これ、System.Text.JsonもやってるというかSystem.Text.Json作ってる人がPRで持ち込んできてるんですよね、そういう実装入れるのは恥じるべき。
